\section{Domain and why time matters}
A fictional football league: six clubs, 60 players, six head coaches and two
seasons.  Contracts start, end and restart, and the paperwork is sometimes late or
wrong.  A payroll clerk, a regulator and an auditor can all ask \emph{``who was FC
Nord's coach on 2 September 2025, as the database knew it on date T?''} and need
different answers: Rusu as known on 5 September, Pop as known on 12 September, and
Rusu again today, after the handover was corrected from 1 to 3 September.  A table
with only valid time cannot give all three.

\section{Modeling decisions}
\textbf{Periods.}  Every version table has \code{valid\_from}, \code{valid\_to},
\code{tx\_from} and \code{tx\_to}, all half-open (\code{from <= x AND x < to});
the seasons follow the same rule.  Valid time is \code{DATE}, since contracts change
by the day; transaction time is \code{DATETIME(6)} in UTC.

\textbf{Sentinels, not NULL.}  Open ends are \code{9999-12-31} and
\code{9999-12-31 23:59:59.999999}, so every predicate stays a plain, indexable range.
\code{TIMESTAMP} is not used: it ends in 2038 and cannot hold the sentinel.

\textbf{Anchor + version.}  \code{agent}, \code{player}, \code{club}, \code{coach}
and \code{season} are non-temporal anchors.  The bitemporal tables are
\code{contract\_version} (the relationship), \code{coach\_assignment\_version} (the
role), \code{player\_value\_version} (the numeric attribute) and
\code{club\_license\_version} (the parent for I2).  \code{calendar\_month} and
\code{query\_params} are helpers, and \code{story\_event} is a hand-written index of
the events, not the data.

\textbf{tx\_registry.}  Each logical change writes one \code{tx\_registry} row, and
every version row it touches gets that \code{tx\_id} and \code{tx\_time}.  An E9
change to a licence, ten contracts and ten values is therefore one transaction.

\textbf{Invariants.}  \code{v\_integrity\_violations} checks I1 (no overlapping
current beliefs per key), I2 (contracts covered by the union of the club's licence
periods), I3 (one coach per club at a time) and that transaction intervals are well
formed (I4).  The immutability part of I4 is enforced by the A1 triggers.

There are no deviations from the modeling rules.

\section{Write protocol: E3, E4 and E8}
Each write sets the clock \code{@sim\_now}, adds a \code{tx\_registry} row, closes
the old belief (only \code{tx\_to} changes) and inserts the new one.
\code{@SENT\_DATE} and \code{@SENT\_TS} are the sentinels.  The A1 procedures follow
the same steps, and the A1 triggers block every other write.

\textbf{E3, late entry.}  On 10 September the clerk records that Pop took over on
1 September.
\begin{lstlisting}
SET @sim_now := '2025-09-10 14:00:00';
INSERT INTO tx_registry (tx_time, author, reason)
VALUES (@sim_now, 'clerk', 'E3 late entry: K2 takes FC Nord');
SET @tx := LAST_INSERT_ID();

UPDATE coach_assignment_version SET tx_to = @sim_now
WHERE coach_id = 1 AND club_id = 1
  AND tx_to = @SENT_TS AND valid_to = @SENT_DATE;

INSERT INTO coach_assignment_version
  (coach_id, club_id, role_title, valid_from, valid_to, tx_from, tx_to, tx_id)
SELECT coach_id, club_id, role_title, valid_from, '2025-09-01', @sim_now, @SENT_TS, @tx
FROM coach_assignment_version
WHERE coach_id = 1 AND club_id = 1
  AND tx_to = @sim_now AND valid_to = @SENT_DATE;

INSERT INTO coach_assignment_version
  (coach_id, club_id, role_title, valid_from, valid_to, tx_from, tx_to, tx_id)
VALUES (2, 1, 'Head coach', '2025-09-01', @SENT_DATE, @sim_now, @SENT_TS, @tx);
\end{lstlisting}

\textbf{E4, correction.}  On 15 September the handover is corrected to 3 September:
both beliefs from 10 September are closed and the corrected pair is inserted.
\begin{lstlisting}
SET @sim_now := '2025-09-15 11:00:00';
INSERT INTO tx_registry (tx_time, author, reason)
VALUES (@sim_now, 'auditor', 'E4 correction: handover was 2025-09-03');
SET @tx := LAST_INSERT_ID();

UPDATE coach_assignment_version SET tx_to = @sim_now
WHERE club_id = 1 AND tx_to = @SENT_TS;

INSERT INTO coach_assignment_version
  (coach_id, club_id, role_title, valid_from, valid_to, tx_from, tx_to, tx_id)
VALUES (1, 1, 'Head coach', '2025-07-01', '2025-09-03', @sim_now, @SENT_TS, @tx),
       (2, 1, 'Head coach', '2025-09-03', @SENT_DATE, @sim_now, @SENT_TS, @tx);
\end{lstlisting}

\textbf{E8, retraction.}  The P6/CS Port contract was never true, so it is closed in
transaction time with no replacement.
\begin{lstlisting}
SET @sim_now := '2026-02-12 09:00:00';
INSERT INTO tx_registry (tx_time, author, reason)
VALUES (@sim_now, 'auditor', 'E8 retraction: P6 at CS Port was never true');
SET @tx := LAST_INSERT_ID();

UPDATE contract_version SET tx_to = @sim_now
WHERE player_id = 6 AND club_id = 2
  AND tx_from = '2026-02-10 10:00:00' AND tx_to = @SENT_TS;
\end{lstlisting}

\section{Challenges and failed attempts}
\textbf{Close + insert in a trigger.}  The first A1 design did the whole protocol in
an \code{AFTER UPDATE} trigger.  MariaDB refuses with \code{ERROR 1442}: a trigger
cannot modify the table that fired it.  The close + insert moved into procedures,
and the triggers only guard.

\textbf{Parameterised AS OF.}  \code{FOR SYSTEM\_TIME AS OF (SELECT known\_at FROM
query\_params)} fails with \code{ERROR 1064}, and a view using a variable fails with
\code{ERROR 1351}.  The native views use literal timestamps instead, one per Q6 date.

\textbf{Dropping the index for EXPLAIN.}  \code{ix\_coach\_asof} also backs the
foreign key on \code{club\_id}, so \code{DROP INDEX} fails (error 1553).  The plan
without it uses \code{IGNORE INDEX} instead.

\textbf{A drifting EXPLAIN estimate.}  Right after loading, the indexed plan
estimated 7 rows instead of 4.  Closing a belief updates \code{tx\_to}, which is in
the index, and InnoDB keeps the old entries until its purge runs.
\code{tools/explain\_q6.sql} now waits for purge first.

\section{Insights: what the engines would enforce}
\textbf{Oracle 23ai.}  Temporal Validity (\code{PERIOD FOR}, \code{AS OF PERIOD
FOR}) covers valid time, and Flashback Data Archive (\code{AS OF TIMESTAMP},
\code{VERSIONS BETWEEN}) keeps an append-only transaction history, which is I4.
I1--I3 would still need constraints or triggers.

\textbf{SQL Server 2022.}  System-versioned tables stamp transaction time and protect
the history table (I4), but there is no valid-time period, so I1--I3 stay manual.

\textbf{PostgreSQL 18/19.}  \code{WITHOUT OVERLAPS} keys would enforce I1 and I3.  A
\code{PERIOD} foreign key enforces I2 only against a single parent period; our
licences have a six-month gap, so I2 would still need a trigger.  \code{FOR PORTION
OF} (19) shortens E4 and E5, but transaction time still needs triggers or an
extension.

\textbf{MariaDB (A2).}  \code{PERIOD FOR} and \code{WITH SYSTEM VERSIONING} reproduce
Q1, Q5 and Q6 with zero differences from the core views.  The costs: the open
transaction end is \code{2106-02-07 06:28:15.999999} instead of 9999, and backdated
history needs the \code{system\_versioning\_insert\_history} loading mode.
