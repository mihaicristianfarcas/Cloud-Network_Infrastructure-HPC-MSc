# Bitemporal football database

Assignment 1, Cloud Databases 2026. Mihai-Cristian Farcaș.

**Engine:** MariaDB 11.8.9 (`mariadb:11.8` Docker image).

A fictional football league with 6 clubs, 60 players, 6 coaches and two seasons.
Every fact has a valid time (when it was true) and a transaction time (when the
database believed it). Q6 shows why both matter: FC Nord's coach on 2 Sep 2025 was
Rusu as known on 5 Sep, Pop as known on 12 Sep, and Rusu again as known today.

## How to run

```bash
docker run -d --name bitemporal-mariadb -e MARIADB_ROOT_PASSWORD=root -p 3307:3306 mariadb:11.8

for f in 01_schema.sql 02_data.sql 03_timeline.sql 04_views.sql 05_tests.sql; do
  docker exec -i bitemporal-mariadb mariadb -uroot -proot < "$f" || exit 1
done

# optional, after 01-05
docker exec -i bitemporal-mariadb mariadb -uroot -proot < 06_advanced_a1.sql
docker exec -i bitemporal-mariadb mariadb -uroot -proot < 06_advanced_a2.sql
```

`01_schema.sql` drops and recreates `football_bitemporal`, so the sequence can be
re-run. Run 01–05 again before re-running 06: the A1 triggers block the direct
writes in 02 and 03.

To ask another question, change the parameters and query a view:

```sql
UPDATE query_params
SET valid_at = '2025-09-02', known_at = '2025-09-12 23:59:59.999999', subject_id = 1;
SELECT * FROM v_q6_bitemporal_point;
```

## Files

| File | Contents |
|---|---|
| `01_schema.sql` | Anchors, 4 bitemporal version tables, `tx_registry` and helper tables |
| `02_data.sql` | E1 initial load in one transaction (generated by `tools/gen_seed.py`) |
| `03_timeline.sql` | E2–E9, one transaction per block, in transaction-time order |
| `04_views.sql` | Q0 (`v_integrity_violations`) and Q1–Q8 |
| `05_tests.sql` | Runs every view; the Q0 and Q2 test writes are rolled back |
| `06_advanced_a1.sql` | A1: write API, 12 guard triggers and negative tests |
| `06_advanced_a2.sql` | A2: Q1, Q5 and Q6 with `PERIOD FOR` and `WITH SYSTEM VERSIONING` |
| `er_diagram.pdf`, `report.pdf` | ER diagram and report |
| `tools/` | Seed generator, extra checks and the EXPLAIN comparison |

Conventions: valid time is `DATE`, transaction time is `DATETIME(6)` in UTC, both
half-open (`[from, to)`, seasons included). Open ends are `9999-12-31` and
`9999-12-31 23:59:59.999999`, never `NULL`. Only `tx_to` is ever updated and
nothing is deleted.

## Notes

- **A1.** `sp_assert_fact`, `sp_end_fact`, `sp_correct_fact` and `sp_retract_fact`
  take the transaction time from `@sim_now`, or `CURRENT_TIMESTAMP(6)` when it is
  not set. The triggers block direct inserts, business-column updates, changes to
  closed rows and deletes. The `@a1_internal` flag is a guardrail, not security; a
  real system would also revoke write privileges on the version tables.
- **A2.** History is loaded with `system_versioning_insert_history = ON`. MariaDB's
  open transaction end is `2106-02-07 06:28:15.999999`, so the 9999 sentinel maps
  onto it. `FOR SYSTEM_TIME AS OF` needs a constant, so Q6 has one view per date.
  All native results match the core views.
- **EXPLAIN.** `tools/explain_q6.sql`: with `ix_coach_asof`, Q6 is a range scan
  (4 rows); without it, a full scan (19 rows). The script waits for InnoDB purge
  first, because right after loading the estimate can read 7.
